# 段階の到達目標までまとめて実装する

2026-10-19からの開発方針。小機能ごとに実装・ユーザーレビュー・Mac比較を待って停止する方式を、依頼された到達目標まで実装と修正を継続する方式へ変更する。過去の進捗文書にある「比較後に次の機能へ進む」という運用上の順序より、この方針を優先する。過去の実測結果・技術的な依存関係・未対応範囲は維持する。

## 作業範囲と継続

- 開始時にユーザーが依頼した段階と完成条件を確認し、現状のコード・固定lock・進捗から実装順を組み立てる。小さな内部作業へ分けても、そのたびに追加の指示を求めない。
- 「全段階をまとめて」の依頼なら下表の1〜6を連続した作業範囲とする。指定段階だけならその範囲まで進める。スキルの変更やレビューだけの依頼を、PHP実装全体への着手指示と解釈しない。
- 依頼内で必要な前段階の不足も補完する。PHP全仕様の網羅を、次段階へ進むための新しい条件にしない。
- 発見した不具合は最小再現例を残してその場で修正する。基盤の状態破壊や既存回帰は、その基盤へ依存する実装より先に直す。外部環境に依存して直せない場合は影響範囲を記録し、独立した作業を進める。
- 進捗は作業中に共有する。実行時間などで継続できない場合は、完了済み範囲・未検証範囲・次の具体的な作業を記録し、完了扱いにしない。

## 確認待ちを挟まない運用

- 同じ依頼の中で、調査・実装・レビュー修正・検証・成功ログの保存・現状文書の更新まで続ける。「修正しますか」「文書に反映しますか」を小工程ごとに尋ねない。既に明示されたcommit・push等の許可も、対象と条件が変わらなければ再確認しない。
- 着手前に完成記録を照合し、達成済みの段階は再実装しない。固定アプリの完成後に残る一般的な未対応機能は、新たに依頼された範囲だけ扱う。
- 番号だけの依頼が複数の作業一覧に当てはまる場合は、対象一覧を一度確認する。その間も共通の読み取り調査や明示されたスキル整備は進める。番号を補うために新しい作業を創作しない。
- 外部検証結果が届いたら、その証拠を確認し、元の依頼に含まれる未完了作業へ続ける。独立した作業が残る間は、環境待ちだけを理由に依頼全体を終了しない。
- スキルの記述だけでは、終了した実行の自動再開や環境権限の変更はできない。継続Goalが明示的に依頼された場合は利用可能な実行機構で扱い、完了・ブロック等の状態は実際の結果とその機構の規則に従う。

## 6段階の到達目標

| 段階 | 対象 | 到達目標と実装順 |
| --- | --- | --- |
| 1 | 項目11 | 参照セル・配列／プロパティ参照 → 参照引数・戻り値・捕捉 → 参照foreach → Iterator／IteratorAggregate／Traversable → Countable／ArrayAccess／Generator。参照と反復を組み合わせた小さなアプリを動かす。 |
| 2 | 項目12・13 | 動的呼び出し・マジックメソッド・clone → Reflection・型情報・属性。小さなDI処理を動かす。 |
| 3 | 項目14・15の必要部分、16 | 固定vendorのautoload経路から必要な標準関数・ファイル操作・autoload登録を補完し、実際のvendor/autoload.phpと対象ライブラリをGo製PHPで実行する。 |
| 4 | 項目14・15の追加部分、17 | Laravelの設定・サービスコンテナ・Console起動に必要な機能を補完し、artisan listと独自コマンドを動かす。 |
| 5 | 項目18〜20 | HTTP入出力・リクエスト状態分離・PDO／SQLite・バリデーション・Eloquentを接続し、LaravelでJSON応答とCRUDを実行する。 |
| 6 | 項目21・22 | API Platformのリソース・シリアライズ・入力検証・CRUD・API仕様出力を接続し、継続実行と性能を検証する。 |

項目14・15は対象アプリの実行経路から必要な機能を選ぶ。依存バージョンと完成条件はリポジトリの固定lock・対象文書を使い、便宜的に別バージョンへ変更しない。Composerによる取得は公式PHPを使えるが、Go製PHPでの起動成功と区別する。

## 実装中の検証と不具合修正

- 既存の公式比較済みfixtureを回帰基準として保つ。最新件数はfixture・期待値・保存ログを照合し、スキルに固定件数を埋め込まない。
- 各変更で意味のある対象テストを実行する。共有基盤の変更後と段階の節目にはmake test・make vet・make build・git diff --checkを実行する。新しい変更や懸念がなければ同じ全件検証を繰り返さない。
- 公式PHPを使える場合、仕様判断が重要な境界や新規ケースは実装中に対象比較する。版別の全件比較は関連変更をまとめた節目に実施する。最終的には対象3版の結果を確認する。
- Podman接続拒否を確認したら、環境に変化がないまま小機能ごとに同じ失敗を繰り返さない。共通の接続失敗ログを参照し、未実行の比較は「未試行／未実施」として、実際に試した環境エラーと分ける。VMを自動再起動しない。
- 比較不能でもGo実装・対象テスト・統合ケースの準備を続ける。公式ソースからの推論と暫定期待値を明記し、Macでまとめて実行できる版別コマンドを残す。環境エラーを無視して合格にしたり、Go出力に期待値を合わせて互換性を主張したりしない。
- 比較できたら差異を再現し、実装を修正して対象再比較、その後に必要な全件比較を行う。診断・出力・終了コードの厳密比較は維持する。

## 記録と完了判定

各段階の進捗文書に、機能、実装状態、ローカル検証、公式比較、統合実行、既知不具合、次の作業を集約する。毎回同じ履歴を複数文書へ積み重ねず、現状の要約から詳細・ログへリンクする。

公式比較待ちは実装を進めるための許可待ちではない。段階間の移行は技術的依存関係で判断する。ただし、公式未比較・統合未実行の段階は「実装済み・検証待ち」であり「完了」とはしない。固定したアプリの完成条件、必要な回帰検証、公式比較が成立して初めて完了と記録する。

commit・push・公開は明示指示がある場合のみ行う。この方針は外部操作の権限を追加しない。

## リリース準備をまとめて依頼された場合

差分整理・再構築・GitHub保存・CIの4項目は開発6段階とは区別する。再構築とCIの修正を先に揃え、生成物・秘密情報の候補を点検する。commit・push・タグ付けまで明示依頼された場合は追加確認を挟まず実施するが、CI未実行を成功と記録しない。権限や接続の制限で公開できなければ独立した準備を完了し、具体的な再実行手順を残す。既存のタグや履歴は上書きしない。
